# Технические решения

Каждое решение записано так: контекст → решение → почему → когда пересматривать. Новые решения добавляются в конец с номером.

## 001. Vite + TypeScript без UI-фреймворка
**Контекст.** Браузерная визуальная новелла: много текста, панелей, состояний кнопок, доступности и адаптивности. Сборка статическая для GitHub Pages. Код будет вести Claude Code.
**Решение.** Vite 8 для сборки и dev-сервера, TypeScript 7 strict, интерфейс на обычном DOM через маленький помощник `el()`.
**Почему.** Из коробки получаем статическую сборку, хеши ресурсов, ошибку сборки при отсутствующем импортированном файле и быстрый dev-сервер. React или Vue почти ничего не дали бы при нескольких экранах и усложнили бы связку с Canvas-эпизодами. Итоговый бандл около 45 КБ JS.
**Пересматривать**, если UI разрастётся до десятков экранов со сложными формами.

## 002. Без игрового движка; Canvas 2D для эпизодов; Three.js — позже и только для фонов
**Контекст.** Бриф просит 2.5D: стилизованные под пиксель 3D-фоны и арены мини-игр, при этом персонажи и UI остаются 2D. Готовых фонов пока нет.
**Решение.** Новелла сделана на DOM/CSS. Мини-игры пишутся на DOM (головоломки, файловый интерфейс) или Canvas 2D (платформеры, погоня), у каждой свой игровой цикл по контракту `EpisodeDefinition`. Phaser или Pixi не подключены. Когда понадобится первый 3D-фон или 3D-арена, подключаем **Three.js** с low-res render target (пиксельный пост-эффект) как рендерер внутри `Stage` и эпизодов, не меняя сценарий и UI.
**Почему.** Текст, выборы, журнал и настройки на DOM читаются лучше, доступнее и проще в тестах, чем текст внутри canvas-движка. Для пяти небольших мини-игр хватает своего цикла на requestAnimationFrame. Phaser весит около 1 МБ и тянет собственную систему сцен, которая дублировала бы рантайм новеллы. Three.js сейчас был бы неиспользуемым кодом. Смешивать движки не будем: для 3D — один Three.js.
**Пересматривать**, когда начнётся мини-игра №1 (платформер). Если физика и коллизии окажутся сложнее простого AABB, оценить подключение лёгкой библиотеки и записать решение здесь.

## 003. Исходники игры лежат в `game/`, а не в корне репозитория
**Контекст.** Pages публикует корень ветки `main`. Если бы в корне лежал исходный `index.html` (со ссылкой на `.ts`), сайт показал бы несобранную, сломанную страницу.
**Решение.** Корень Vite — `game/`, сборка идёт в `dist/` (в git не попадает). В корень копируется только готовая сборка (см. 012).

## 004. Проверки в GitHub Actions
На pull request и push в любую ветку, кроме `main`, работает `ci.yml`: typecheck, unit-тесты, сборка, e2e. Разрешение `contents: read`, секреты не нужны. Как публикуется `main`, описано в 012.
*История:* сначала публикация шла через `actions/deploy-pages`. От неё отказались, потому что для неё нужно переключать Settings → Pages на «GitHub Actions», а автор хочет сохранить режим «из ветки `main`».

## 005. `base: './'` (относительные пути)
**Почему.** Одна сборка работает на `localhost`, по адресу `/Geometry-of-love/` и при переименовании репозитория. E2E-тесты отдают сборку именно под `/Geometry-of-love/`.

## 006. Сценарий хранится в TypeScript-данных, а не в JSON или YAML
**Почему.** Типы ловят опечатки ещё при написании, автодополнение помогает, парсер не нужен. Целостность ссылок (сцены, позы, переменные) дополнительно проверяет `validateStory` в тестах. Если сценарий будут писать не через Claude, можно добавить импорт из текстового формата, сохранив модель `Story`.
**Риск.** Сохранения и прочитанные реплики хранят индекс шага. Вставка шагов в уже выпущенную сцену сдвигает позицию в старых сохранениях. Перед релизами с изменением выпущенных сцен нужна миграция (`SAVE_SCHEMA`) или стабильные id реплик.

## 007. Листы спрайтов не нарезаются
**Решение.** Позы описаны прямоугольниками кадров на исходных листах и показываются через `background-position`.
**Почему.** Исходники не меняются и не копируются, а границы кадров проверяются тестом. Нарезанные PNG всегда можно сделать позже скриптом, если понадобятся отдельные файлы.

## 008. Сохранения в localStorage
**Почему.** GitHub Pages — статический хостинг без сервера. Формат версионирован (`SAVE_SCHEMA`), повреждённые данные распознаются. Если localStorage недоступен (приватный режим), игра работает в памяти и предупреждает игрока.
**Ограничение.** При очистке браузера или на другом устройстве сохранения теряются. Облачные сохранения требуют отдельного сервиса и согласования.

## 009. Только TypeScript strict, без ESLint и Prettier
**Почему.** Strict с `noUnusedLocals` и `noUncheckedIndexedAccess` ловит основное, а меньше инструментов — меньше конфликтов и ожидания. Стиль кода держится единым по образцу существующих файлов.
**Пересматривать**, если над кодом начнут работать несколько людей одновременно.

## 010. Пиксельный шрифт Tiny5
Pixelify Sans попробовали и отказались: кириллица читается плохо. Tiny5 из `@fontsource` (OFL) лежит прямо в сборке, без запросов к Google Fonts.

## 011. Исходные материалы перенесены в `materials/`
Синопсис, бриф и ТЗ лежат в `materials/docs/`, референсы — в `materials/references/` (через `git mv`, история сохранена). Спрайты Мелоди перенесены в `game/src/assets/characters/melody/` под понятными именами: `IMG_4966.png` → `melody-sheet-01.png`, `IMG_5064.png` → `melody-sheet-02.png`. Содержимое файлов не менялось. Ссылок на старые пути не было: README был пустым. Вернуть прежнее расположение можно через `git mv`.

## 012. Публикация из ветки `main` с готовой сборкой в корне
**Контекст.** Автор настроил Pages как «Deploy from a branch: `main` / (root)» и хочет, чтобы игра открывалась именно так, без изменения настроек.
**Решение.** Готовая сборка (`index.html`, `assets/`, `.nojekyll`) коммитится в корень `main`. Workflow `deploy.yml` на каждый push в `main` прогоняет все проверки, выполняет `npm run build:pages` и, если сборка изменилась, коммитит её обратно в `main` от имени `github-actions[bot]`. Встроенный процесс GitHub «pages build and deployment» публикует этот коммит. Собственные коммиты workflow не запускают его повторно: push через `GITHUB_TOKEN` не создаёт новых запусков, а пути сборки дополнительно исключены через `paths-ignore`. `.nojekyll` отключает обработку Jekyll.
**Почему.** Ручные настройки не нужны, и опубликованная версия проходит те же проверки, что и PR. Сборка детерминирована (одинаковые хеши при повторной сборке), поэтому лишних коммитов нет.
**Цена.** В истории `main` появляются коммиты со сборкой (около 330 КБ на версию, в основном спрайты; меняются они редко, а JS и CSS весят около 60 КБ). Если история разрастётся, можно перейти на Settings → Pages → «GitHub Actions» и `actions/deploy-pages` (см. историю в 004).

## 013. Тестовый хук для мини-игр на реакцию
**Контекст.** Браузерные тесты должны проходить всю историю, но платформер и погоню скрипт стабильно не пройдёт (тайминги, частота кадров).
**Решение.** Отдельная сборка `vite build --mode e2e` с `VITE_E2E_HOOKS=1` (`game/.env.e2e`) открывает `window.__golTest.winEpisode()`. В production условие ложно на этапе сборки, код удаляется; CI проверяет, что в `dist/` хука нет. Правила этих мини-игр покрыты unit-тестами (достижимость платформ, интервалы препятствий, хитбоксы), остальные мини-игры e2e проходит по-настоящему.
**Почему.** Игроку пропуск недоступен (требование: мини-игры обязательны), а тесты остаются полными и стабильными.

## 014. Сцены «исследования» как хаб выбора
Синопсис говорит об исследовании Песочницы и архива, а автор запретил свободное перемещение. Решение: выбор «к кому подойти / что изучить», который повторяется, пока не пройдены все пункты (ветвление перед выбором выводит дальше). Валидатор допускает выбор из одних условных вариантов только при таком ветвлении прямо перед ним.
