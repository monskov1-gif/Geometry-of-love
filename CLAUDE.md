# Geometry of Love — инструкции для Claude Code

Браузерная сюжетная визуальная новелла (психологический хоррор) с обязательными сюжетными мини-играми. Публикуется на GitHub Pages из корня ветки `main`: https://monskov1-gif.github.io/Geometry-of-love/
**Игра проходится целиком: 15 глав, эпилог, 3 концовки, 5 мини-игр. Графика, кроме 4 спрайтов Мелоди, временная; диалоги — черновик по синопсису, правки автора приоритетны.**

## Источники и их приоритет
1. Прямые указания автора в переписке.
2. Сюжет: `materials/docs/Geometry of love Синопсис.pdf`. Это канон событий, персонажей, развилок и концовок.
3. Визуальный бриф: `materials/docs/Geometry_of_Love_art_brief.docx`, выжимка лежит в `docs/ART_BRIEF.md`.
4. Спрайты (`game/src/assets/`) и референсы (`materials/references/`, индекс в `materials/README.md`).
5. Технические решения: `docs/DECISIONS.md`.
Полное ТЗ автора: `materials/docs/Geometry_of_Love_technical_description.docx`.

Не меняй канон и художественное направление без разрешения. Пробелы в источниках фиксируй в `docs/GAME_DESIGN.md` («Открытые вопросы») и не выдавай свои предположения за канон.

## Жёсткие правила геймдизайна (от автора)
- Это визуальная новелла. Свободного исследования, открытого мира и RPG-управления нет.
- Перемещение есть только в интерактивных эпизодах и только влево-вправо. Прыжки и приседания разрешены только внутри мини-игр, которые синопсис прямо называет платформерами (№1, №3, №5).
- Сюжетные мини-игры обязательны: сюжет продолжается только после подтверждённого успеха. При неудаче даётся повтор, пропуска нет.
- Конкретные мини-игры, реплики и названия качеств Дамео не придумывай: бери их из источников или спроси автора.

## Команды
```
npm ci               # установить зависимости
npm run dev          # локальный запуск: http://localhost:5173/
npm run check        # typecheck + unit-тесты + production build
npm run test:e2e     # Playwright: сборка, отдача по /Geometry-of-love/, десктоп + мобильный
SHOTS_DIR=/path npm run test:e2e   # то же, плюс скриншоты каждого этапа
npm run build:pages  # собрать и скопировать сборку в корень (index.html + assets/) для Pages
```

## Структура (подробно в docs/ARCHITECTURE.md)
- `game/src/core/` — чистая логика без DOM: типы сценария, рантайм, условия и эффекты, сохранения, валидатор.
- `game/src/content/` — данные: сцены (`story/volume-1..3.ts`), персонажи и спрайты, фоны, переменные, концовки, задачи.
- `game/src/episodes/` — мини-игры и интерактивные эпизоды (контракт описан в `episodes/types.ts`).
- `game/src/platform/` — localStorage, настройки, мета-прогресс, ввод, загрузка ресурсов.
- `game/src/ui/` — DOM-экраны и компоненты. `game/src/styles/` — токены и стили.
- `tests/unit` (Vitest), `tests/e2e` (Playwright). `materials/` — исходники автора, только для чтения.
- `index.html`, `assets/`, `.nojekyll` в корне — **сгенерированная** сборка для GitHub Pages. Не редактируй их руками: исходный код игры лежит в `game/`.

## Работа с кодом
- Перед изменением незнакомого модуля прочитай его и всех, кто его вызывает. Расширяй существующие системы. Не переписывай их и не дублируй.
- Сюжетная логика живёт только в данных сцен и в `core`. UI только отображает `Presentation` и вызывает `advance/choose/completeEpisode`.
- Состояние UI (Auto, Skip, открытые панели) не попадает в сохранения. Открытие панели никогда не продвигает сюжет.
- Не удаляй работающие механики ради упрощения. Не подменяй рабочую механику декоративным макетом.
- Каждая кнопка выполняет реальное действие. Функции, которой нет, нет и в интерфейсе.
- Ошибки загрузки ресурсов, сохранений и сценария показывай игроку и пиши в консоль. Пустых `catch` и отключённых проверок быть не должно.
- Файлы держи небольшими, с одной ответственностью. Новая зависимость допустима только с обоснованием в `docs/DECISIONS.md`.
- При изменении формы `StoryState`/`SaveData` повышай `SAVE_SCHEMA`, добавляй миграцию и тест. Не меняй порядок шагов в выпущенных сценах без предупреждения: сохранения хранят индекс шага.

## Ресурсы
- Исходники в `materials/` и спрайты не меняй, не пережимай и не переименовывай без причины. Позы задаются прямоугольниками кадров в `content/characters.ts`.
- Не растягивай спрайты, не меняй их пропорции и палитру. Пиксель-арт всегда `image-rendering: pixelated`, а текст пикселизации не подвергается.
- Отсутствующую графику заменяет подписанная заглушка («ВРЕМЕННАЯ ЗАГЛУШКА»), а не картинка из референсов.
- Цвета и шрифты берутся только из `styles/tokens.css`. У каждого пространства (reality / app / game / code) своя палитра.

## Git и публикация
- Перед работой и после неё проверяй `git status`. Чужие незакоммиченные изменения не трогай.
- Без явного разрешения автора не делай commit, push, merge в main, force push, `reset --hard`, массовое удаление и изменение настроек GitHub.
- Работа идёт в отдельной ветке и проходит через PR в main. После merge `.github/workflows/deploy.yml` проверяет и пересобирает игру и коммитит сборку в корень `main`, а Pages публикует её оттуда.

## Проверка и отчёт
- Не утверждай, что тест прошёл, если ты его не запускал. Не утверждай, что «работает в браузере», если проверял только код.
- Различай три состояния: «проверено автоматически», «проверено вручную в браузере», «не проверено».
- Для визуальных изменений делай скриншоты (desktop и mobile) и смотри на них сам.
- После исправления ошибки добавляй тест, который её ловит.
- В конце сообщай: какие файлы изменены, какие проверки запущены и с каким результатом, что осталось нерешённым.

## Агенты и навыки
Агенты лежат в `.claude/agents/`: game-architect, gameplay-developer, visual-ui-developer, qa-tester, code-reviewer. Не запускай двух агентов, которые редактируют одни и те же файлы. Параллельно можно гонять только анализ, тесты и задачи с разными областями.
Навыки лежат в `.claude/skills/`: `/preflight`, `/new-scene`, `/new-mechanic`, `/fix-bug`, `/release-check`.
Хук `.claude/hooks/check-after-edit.mjs` после правки `.ts`-файлов запускает typecheck (и валидатор контента для `content/`). Файлы он не меняет.
